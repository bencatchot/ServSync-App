## Retention and bounded storage

- A cycle starts at its database-generated creation timestamp and expires exactly **720 hours** later. Neither activity nor refresh extends it. The expiry is prominently displayed in UTC. A DST regression test verifies the fixed duration.
- In-app warnings become visible when remaining time is at most 168 hours and 24 hours. They are evaluated using the server clock offset; the server independently rejects expired writes. No email, SMS or external notification is sent. Offline users may miss warnings.
- Expired snapshots, Drafts, files and transfer payloads are denied by database RLS, even through direct ordinary-role SQL. A separate owner-checked function exposes only cycle status and a null expired snapshot. A fresh cycle may snapshot current permitted setup without modifying live data. This harness uses only the current fictional fixture. No early destructive reset is exposed.
- Per cycle: 50 Drafts, 100 lines per Draft/template, 500 prices, 50 templates, 1 MiB per snapshot/Draft/transfer payload; 10 generated PDF files, at most 5 MiB each and 20 MiB combined; 20 transfer reviews over the cycle. Only one active cycle per contractor. Starting a new cycle atomically removes that owner’s expired local content, so unresolved transfers cannot accumulate old cycles or block a fresh start. File limits apply transactionally under the same workspace lock as cleanup.
- Files are owned bytes, stored in the isolated test database, with no source/shared object path. The local UI generates/downloads PDFs without retaining server copies; the bounded file persistence/purge path is exercised by database tests. Cloud object storage, multipart uploads and orphan-object reconciliation are not implemented.
- `practiceCleanupDryRun()` reports expired cycles, counts/bytes and transfer blocks. The review harness exposes only this read-only report. There is **no scheduled purge or HTTP operator-cleanup execution**. An explicit fresh start also removes only that owner’s expired local cycle content as part of its transaction.
- `applyDisposableCleanup()` is test-only: the SQL function checks the exact database name, disposable marker, workspace ID, expected expiry under a lock. Transfer identities are detached from expiring content. The ordinary app role cannot execute it. It removes only that expired cycle's Drafts, transfer packages and generated bytes. A fresh cycle, other tenants and destination records are excluded. Concurrent runs are idempotent. Installation refuses a normal ServSync/Supabase database.
- A `committing` transfer no longer blocks content cleanup or fresh starts. Beginning a transfer atomically creates a detached, payload-free operation ledger. It stores only operation/contractor/workspace IDs, package hash, admission deadline, result/destination ID and retry/retention metadata. Access expires after 90 days; physical pruning requires cleanup. Ordinary users cannot read its table; an owner-checked status function exposes their metadata. A separate recovery role has execute-only access to bounded functions and cannot read expired content or create destination Drafts.
- The local recovery helper atomically claims at most 20 identities per invocation using a five-minute lease, with at most 12 automatic attempts spaced by a stored one-hour retry time. Concurrent workers cannot claim the same eligible operation; stale retry results cannot consume more attempts or overwrite a terminal outcome. It surfaces `needs_review` after repeated unknown outcomes. Terminal results are idempotent. No scheduler is enabled; worker execution and retention enforcement still require operational setup. Expiry removes access immediately, while physical deletion occurs on explicit local cleanup or a fresh start.
- Recovery metadata can be pruned after 90 days, including unresolved records, with unresolved removals explicitly counted. This bounds retained source metadata; it does **not** assert that a destination write failed. After that window, automated source recovery is unavailable. An actual destination Draft retains its unique operation identity and package hash for its own lifetime, independent of receipt retention. Destination records are never purged by Practice cleanup.

## Transfer review and minimal receipts

The browser saves a versioned Practice Draft, then requests an immutable transfer review valid for at most ten minutes and never beyond cycle expiry. Server validation recalculates totals and removes synthetic customer/property identifiers, private notes, costs and lifecycle state. The reviewer sees the destination, exact total, kept explicit prices, no assigned real customer/property, and a button explicitly approving one test Draft. Cancel creates nothing.

The test destination is a **separate local database**, not the real live tables. A successful transfer creates a new unsent `draft` and a receipt in one destination transaction, then discards the Practice package payload when acknowledgement completes. No provider, email, invoice numbering, approval, payment, schedule, Home History or integration operation is invoked. The database mints a timestamp-bound operation ID; the client’s separate request ID supports review retries. The operation ID binds its package hash and source revision, and its original ten-minute admission window cannot be renewed even after metadata is pruned. Stale edits, altered hashes, revoked ownership and repeated commits are rejected or recover the original receipt. Initial Draft creation also reuses a client-generated ID after a lost response rather than blindly inserting another record.

Minimal destination receipt fields: operation ID, contractor ID, package hash, destination ID, created-at and expires-at. Proposed retention is **2160 hours (90 days)** to cover interrupted-response recovery and investigation without keeping the copied payload in audit. Completed Practice transfers clear their payload immediately. Retention tests remove expired receipt metadata without deleting the destination Draft, and prove terminal transfers cannot replay. A scheduled receipt-retention worker is not enabled. The synthetic destination permanently binds operation ID and package hash on the resulting Draft. Ephemeral receipt/cancellation-fence rows expire after 90 days; replay after their pruning still cannot renew the operation’s timestamp-bound admission deadline. Real live implementation must preserve this contract and separately approve its permanent Draft provenance fields.

If destination commit succeeded but source acknowledgement failed, recovery finds the original destination identity, even after receipt or source-content deletion. Privileged recovery can resolve an already-authorized write after ownership revocation without granting the revoked user access. If no destination exists before the admission deadline, recovery waits. After the deadline, it serializes cancellation against commit using the same destination operation lock, then writes a cancellation fence. A missing receipt alone never proves cancellation. An unavailable destination produces an unknown result and bounded retries, never a new write.

`acceptPreparedTestTransfer` accepts only a trusted server-prepared package; the browser cannot supply payload/deadline to that function. The destination checks the immutable operation-ID deadline after acquiring the lock. A future hosted gateway must authenticate that package and retain the same bounds. Local SQL roles and synthetic actor context do not implement a production trust channel.

## Snapshots and limitations

Snapshot parsing reconstructs an explicit allowlist: business display name/default labor rate, selling Price Book fields, template names/scopes/lines. There is no raw profile/record clone. Credentials, auth users/sessions, invitations, subscription/admin fields, private costs, external IDs, payment tokens, accounting links, signatures, actual customer records and invoice numbers are not copied.

Refresh requires a review and expected snapshot revision. It changes only the setup snapshot, preserving already saved Draft scopes/prices. Editing the source Price Book/template inside Practice and three-way refresh conflict merging are later work. This first slice has no two-way synchronization. The local fixture uses zero tax; real jurisdiction/tax/customer mapping and live price-change review are blockers for the real importer.

Practice PDFs have a visible marker on every page and a `PRACTICE-` filename. Ordinary PDF output remains unchanged. Mobile-web preview/download is tested; native Capacitor share/save and other document types are not enabled or claimed in this slice. Private notes/location fields are hidden in the restricted Practice composer instead of accepting text that the allowlist would discard. A person may manually forward a downloaded document; the no-delivery promise covers app/provider actions.

## Run and inspect locally

Requires Node/npm dependencies and PostgreSQL server/client binaries (validated on PostgreSQL 16). No environment file or real credential is needed.

```sh
npm run typecheck:practice
npm run test:practice
npm run practice:local
# In a second terminal, while the local harness is running:
npm run test:practice:browser
```

Local review: `http://127.0.0.1:5193/scripts/practice/index.html`. It binds loopback only; it is not a public/cross-device URL. `PG16_BIN` may point to installed PostgreSQL binaries; the default is Homebrew PostgreSQL 16. The harness starts a uniquely named cluster under `/tmp/servsync-practice-*`, listens on a Unix socket, and closes/removes only that newly created synthetic fixture when stopped. Data persists across requests and independent browser contexts while the server runs. A real hosted workspace must survive service restarts and be cross-device; that deployment is not represented by this disposable harness.

## Retention truth and review scope

Thirty days is an access/cycle boundary, not a guaranteed physical-erasure time. Without a deployed scheduler, expired rows remain on disk until local cleanup/fresh start. Database/WAL/backups and any separately operated backups have their own retention. Restore procedures must reapply expiry and deletion before reopening access; neither expired content nor stale transfer admission may be resurrected by restoring an old backup. Cross-database restore consistency and recovery after loss/rollback of the destination’s permanent operation identity remain explicit hosted rollout gates. No production deletion, backup change or persistent job was enabled.

The 90-day minimal receipt/ledger limit does not apply to an intentionally created destination Draft or its permanent operation identity. A prolonged destination outage can outlast source recovery metadata: report the result as unknown, inspect destination provenance if later available, and never silently recreate the write. This is a truthful bounded-retention compromise, not a guarantee that every partition resolves automatically.
