# Temporary contractor Practice — local foundation

Implementation issue: [#587](https://github.com/bencatchot/ServSync-App/issues/587). Branch: `codex/temporary-practice-workspace`, based on main `5ea8fec`. This is independent of onboarding PR #586. **Local/test foundation only; no hosted Practice capability or live importer is released.**

## Approved direction and initial scope

Ben approved beginning the recommended owner-only Practice workspace with fictional customers, business/pricing/template snapshots, and explicit create-only transfer review. He requested roughly monthly cleanup and clear notice. **30 days, seven-day and one-day warnings are implementation defaults proposed for review**, not an assertion that he chose those precise periods.

The initial slice implements a real disposable PostgreSQL persistence boundary, owner-scoped RLS, versioned Draft saves, bounded snapshots/files, expiry/quota guards, dry-run cleanup, transfer review, and an executable separate-database transfer/receipt model. The local screen reuses `ContractorDraftComposer`, Price Book/template selection, canonical money calculations, and the actual Estimate PDF renderer. It is deliberately absent from the normal application entry point/build. Shared components gain optional props with unchanged defaults.

The local server uses one fixed synthetic owner; it does **not** authenticate a real account. The role/tenant tests exercise actual PostgreSQL policies using trusted server actor context. They do not prove a deployed account handoff, Supabase JWT integration, remote storage policy or Production isolation.

## Retention and bounded storage

- A cycle starts at its database-generated creation timestamp and expires exactly **720 hours** later. Neither activity nor refresh extends it. The expiry is prominently displayed in UTC. A DST regression test verifies the fixed duration.
- In-app warnings become visible when remaining time is at most 168 hours and 24 hours. They are evaluated using the server clock offset; the server independently rejects expired writes. No email, SMS or external notification is sent. Offline users may miss warnings.
- Expired payloads are omitted by the gateway. A fresh cycle may snapshot current permitted setup without modifying live data. This harness uses only the current fictional fixture. No early destructive reset is exposed.
- Per cycle: 50 Drafts, 100 lines per Draft/template, 500 prices, 50 templates, 1 MiB per snapshot/Draft/transfer payload; 10 generated PDF files, at most 5 MiB each and 20 MiB combined; 20 transfer reviews over the cycle. At most two retained cycles per contractor, preventing unchecked accumulation when cleanup is disabled or blocked. File limits apply transactionally under the same workspace lock as cleanup.
- Files are owned bytes, stored in the isolated test database, with no source/shared object path. The local UI generates/downloads PDFs without retaining server copies; the bounded file persistence/purge path is exercised by database tests. Cloud object storage, multipart uploads and orphan-object reconciliation are not implemented.
- `practiceCleanupDryRun()` reports expired cycles, counts/bytes and transfer blocks. The review harness exposes only this read-only report. There is **no scheduled purge or HTTP cleanup execution**.
- `applyDisposableCleanup()` is test-only: the SQL function checks the exact database name, disposable marker, workspace ID, expected expiry and current transfer state under a lock. The ordinary app role cannot execute it. It removes only that expired cycle's Drafts, transfer packages and generated bytes. A fresh cycle, other tenants and destination records are excluded. Concurrent runs are idempotent. Installation refuses a normal ServSync/Supabase database.
- A `committing` transfer blocks cleanup and fresh-start creation until reconciliation. This deliberate exception may retain a bounded expired payload longer than 30 days. No claim of guaranteed deletion at expiry is made. Production needs monitoring and a bounded reconciliation process before rollout; if the destination outcome cannot be established, stop and surface the blocked cycle rather than guessing or erasing evidence.

## Transfer review and minimal receipts

The browser saves a versioned Practice Draft, then requests an immutable transfer review valid for at most ten minutes and never beyond cycle expiry. Server validation recalculates totals and removes synthetic customer/property identifiers, private notes, costs and lifecycle state. The reviewer sees the destination, exact total, kept explicit prices, no assigned real customer/property, and a button explicitly approving one test Draft. Cancel creates nothing.

The test destination is a **separate local database**, not the real live tables. A successful transfer creates a new unsent `draft` and a receipt in one destination transaction, then discards the Practice package payload when acknowledgement completes. No provider, email, invoice numbering, approval, payment, schedule, Home History or integration operation is invoked. The source review ID binds its package hash and source revision. Stale edits, altered hashes, revoked ownership and repeated commits are rejected or recover the original receipt. Initial Draft creation also reuses a client-generated ID after a lost response rather than blindly inserting another record.

Minimal destination receipt fields: operation ID, contractor ID, package hash, destination ID, created-at and expires-at. Proposed retention is **2160 hours (90 days)** to cover interrupted-response recovery and investigation without keeping the copied payload in audit. Completed Practice transfers clear their payload immediately. Retention tests remove expired receipt metadata without deleting the destination Draft, and prove terminal transfers cannot replay. A scheduled receipt-retention worker is not enabled. Before real rollout, receipt pruning must exclude unresolved transfers and preserve sufficient terminal identity to prevent replay; that is a live-gateway contract, not permission to delete live records.

If destination commit succeeded but source acknowledgement failed, retry recovers the original receipt. If a transfer is `committing` and no destination receipt can be verified, the harness fails closed and requires reconciliation; it does not blindly retry or create a second operation.

## Snapshots and limitations

Snapshot parsing reconstructs an explicit allowlist: business display name/default labor rate, selling Price Book fields, template names/scopes/lines. There is no raw profile/record clone. Credentials, auth users/sessions, invitations, subscription/admin fields, private costs, external IDs, payment tokens, accounting links, signatures, actual customer records and invoice numbers are not copied.

Refresh requires a review and expected snapshot revision. It changes only the setup snapshot, preserving already saved Draft scopes/prices. Editing the source Price Book/template inside Practice and three-way refresh conflict merging are later work. This first slice has no two-way synchronization. The local fixture uses zero tax; real jurisdiction/tax/customer mapping and live price-change review are blockers for the real importer.

Practice PDFs have a visible marker on every page and a `PRACTICE-` filename. Ordinary PDF output remains unchanged. Mobile-web preview/download is tested; native Capacitor share/save and other document types are not enabled or claimed in this slice. Private notes/location fields are hidden in the restricted Practice composer instead of accepting text that the allowlist would discard. A person may manually forward a downloaded document; the no-delivery promise covers app/provider actions.

## Run and inspect locally

Requires Node/npm dependencies and PostgreSQL server/client binaries (validated on PostgreSQL 16). No environment file or real credential is needed.

```sh
npm run typecheck:practice
npm run test:practice
npm run practice:local
# In a second terminal, while the local harness is running:
npm run test:practice:browser
```

Local review: `http://127.0.0.1:5193/scripts/practice/index.html`. It binds loopback only; it is not a public/cross-device URL. `PG16_BIN` may point to installed PostgreSQL binaries; the default is Homebrew PostgreSQL 16. The harness starts a uniquely named cluster under `/tmp/servsync-practice-*`, listens on a Unix socket, and closes/removes only that newly created synthetic fixture when stopped. Data persists across requests and independent browser contexts while the server runs. A real hosted workspace must survive service restarts and be cross-device; that deployment is not represented by this disposable harness.

## Validation evidence

The committed tests use actual local PostgreSQL, not mocked persistence. They cover save/resume and duplicate creation, RLS across tenants/absent role/revoked owner, ownership reassignment denial, input allowlists, prices/totals/limits, warning thresholds, fixed expiry, stale review, explicit transfer approval, cancellation, lost acknowledgement recovery, exact cleanup target, dry-run nonmutation, concurrent cleanup, active-transfer protection, concurrent Draft/file quotas, fresh-cycle and destination preservation, finite receipt retention, and SQL/remote-target rejection.

Browser tests use isolated Chromium desktop and WebKit mobile, with real local API/database requests: save, refresh/resume from another browser context, PDF preview/download, cancel then approve synthetic transfer, no horizontal overflow, console errors or external network requests. Additional checks reject provider/cleanup routes and cross-origin writes, and verify every page of a multi-page Practice PDF is marked while ordinary PDFs are unmarked. These do not verify deployed authentication, actual mobile devices, native sharing, real account data or live transfers.

## Remaining rollout gates

1. Approve the concrete isolated backend/infrastructure and costs; provision only after approval. No persistent credentials or paid resources were created.
2. Implement/review the same-account, one-use handoff, session revocation, trusted actor/tenant binding, least-privilege deployed connection and RLS/storage policies. Local actor context is not a production authentication design.
3. Build a permission-checked business snapshot exporter and real live Draft importer with customer/property mapping, current-price/tax revalidation, idempotent atomic receipt, conflict handling and reconciliation. The synthetic destination is a test contract only.
4. Review exact retention defaults, production quotas, monitoring, backup/replica/log retention and eventual physical deletion. PostgreSQL deletion alone does not erase backups or return all disk space immediately. No production purge is enabled.
5. Verify hosted cross-device and service-restart durability, tenant/security/provider-denial tests, native/mobile behavior as applicable, and operational recovery. Rollout/merge remain separate approvals.
